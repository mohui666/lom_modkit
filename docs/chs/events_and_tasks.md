# 事件与任务配置

本机开发分支 `codex/event-task-modes`，要求 MortalModHost 1.1.3。编辑器保留原有工作区和三栏布局，作品级设置与剧情内容分层。

## 两种作品

| 模式 | 新建入口 | 运行方式 |
| --- | --- | --- |
| `addon` 原版附加剧情 | 文件 → 新建原版附加剧情 | 在原版存档流程中按条件触发，保留原版任务优先顺序，不创建独立战役 |
| `sandbox` 自由剧本 | 文件 → 新建自由剧本 | 从标题页进入隔离存档，使用自己的开场事件，可以禁用原版事件 |

旧作品没有 `play_mode`，仍走旧 v3 战役契约，不自动重写旧任务、旗标或章节。附加剧情不参与其他 MOD 的战役；独立作品只调度当前作品的事件。多个附加包依现有文件名加载顺序匹配，各包事件池和状态独立。

## 配置与保存

`manifest.json` 保存作品身份、`play_mode`、兼容性与开局设置；独立的 `scenario.json` 保存事件和任务；`story/*.json` 保存演出章节。

作品名旁的“作品设置…”（或文件 → 作品设置）管理整部作品。左侧“剧情内容”编写对话、选项和演出；“剧情安排”列出事件，下面的“任务进度（可选）”记录跨事件流程。选中一项后，中间只编辑该项，右侧显示关联剧情或事件。

事件直接选择年份、月份、上／中／下旬，再选择地点、剧情、概率与是否重复。游戏没有逐日日期，不提供“几号”的选择。“前置任务”和“剧情结束后做什么”可选；编号、条件树、权重池及完整结果动作放在高级设置。

例如“七月来信”：时间选不限年份、7 月、不限旬；自动发生，30% 概率，不重复，每月再尝试。只想固定在第 2 年 7 月上旬发生，就分别选择第 2 年、7 月、上旬。剧情下拉框显示作品内的标题，内部仍保存原章节 ID。

这两类配置分别编辑 `scenario.json` 的 `events` 和 `tasks`。配置随作品一起保存、撤销、恢复、导出和重新导入。带配置的作品必须保存为项目目录或 `.lommod`，不能另存成单一章节 JSON 而丢弃配置。

`manifest.play_mode` 为 `addon` 或 `sandbox`，`min_host_version` 至少 1.1.3。保留 v3 稳定 `campaign_id`：附加剧情只用它区分自己的存档状态，不创建 MOD 槽。附加剧情的 `campaign.new_game=false`，自由剧本为 true。新模式不能混用 `campaign.triggers`。

## 事件

顶层配置为 `{"schema":1,"events":[],"tasks":[]}`。自由剧本另有 `entry_event`，指向唯一开场事件，其章节与 `manifest.entry` 一致。

| 字段 | 含义 |
| --- | --- |
| `id`、`name` | 稳定事件 ID 与显示名称 |
| `trigger` | `start` 开场、`auto` 自动触发、`position` 点击地点 |
| `position`、`script` | 地点 ID（仅地点事件）和同包演出章节 ID |
| `enabled` | 是否启用，默认 true |
| `once` | 默认 true，完成演出后不再发生；false 表示可重复 |
| `check` | `month` 每月、`stage` 每旬、`action` 每次行动；默认每旬 |
| `priority` | 越大越优先，同优先级按配置顺序 |
| `chance` | 0～100 的实际发生概率，默认 100，允许小数 |
| `pool`、`weight` | 可选事件池和相对权重；默认权重 1 |
| `weight_modifiers` | 按条件增减权重，最低归零 |
| `when` | 组合条件；`{"all":[]}` 表示不限制 |
| `outcomes` | 演出结果与结算配置，必须包含 `completed` |

重复性与判定周期分别设置。`once=false, check=action` 可在同一个月多次发生；`once=false, check=month` 每月可以重新发生。一次性事件概率失败后，下个判定周期仍可再试；完成演出后退出候选池。

未抽中也消耗本周期的判定，读档或反复进出场景不会在同一存档状态中重抽。行动周期使用“年、月、旬、剩余行动次数”；事件不额外扣点，地点行动沿用原版扣点流程。

同池候选必须使用相同入口、地点、优先级和周期。先筛选条件，再判定各候选的 `chance`，最后按正有效权重抽取一项，参与判定的候选消耗本周期机会。权重 30:70 表示双方符合条件时按这个比例抽取，不是两个独立百分比。

## 条件与任务

组合条件使用 `all/any/not`，最多 12 层；空 `all` 为真，空 `any` 为假。叶条件示例：

```json
{"source":"time","key":"month","op":"eq","value":7}
```

来源支持 `time/stat/affinity/flag/game_flag/variable/task`。时间字段为 `year/month/stage/action`；`flag` 是剧情记录是否存在（0/1），`game_flag` 是原版数值旗标，`variable` 是作品自有 Int32 变量（缺省 0）。任务状态支持 `eq/ne`，数值支持 `eq/ne/lt/le/gt/ge`。缺失原版属性或旗标明确报错，不能在 NOT 条件下变成成功。

任务定义 `id/name/states/initial`，可选 `transitions`。每次调度基于同一任务状态快照，每个任务最多执行一个条件转换；随后事件读取更新后的状态。事件结果也可直接推进任务：

```json
{
  "completed": {
    "tasks": {"delivery":"completed"},
    "variables": {"visits":{"op":"add","value":1}},
    "actions": [{"type":"stat","key":"money","op":"add","value":50}]
  }
}
```

最多 256 个任务（每项 1～32 个状态）、512 条事件。保存的任务状态若已不在修改后的配置中，会报告不兼容，不静默清空。

## 章节与结果

章节保留对白、人物演出、选项、分支和玩法场景。事件登记、任务推进、变量写入、时间、数值和奖励放在独立配置，新模式不能在章节中使用对应状态修改节点或 `raw`。旧格式继续兼容。

结束节点填写 `event_result`，例如 `accepted/declined`，不填则为 `completed`。每个最终章节结果都必须在事件的 `outcomes` 中定义。它不能与 `next_script` 同时填写；跨章节演出保留当前事件直到最终回报。

结果动作支持：

- `stat/affinity/game_flag`：`key`、`op=set/add`、Int32 `value`。
- `flag`：`key`，记录剧情标记。
- `talent`：`key`、`value=1/-1`。
- `item`：`key`、`kind=book/misc/special`、`op=add/remove`、正整数 `value`；`remove` 按 `value` 减少数量，使用原版 `AddItem` / `AddCount` 的归零规则。
- `time`：`year/month/stage`，设置明确游戏日期。

宿主先验证结果、原版 ID、变量溢出和最终状态的 128 KiB 编码上限，再执行结果动作并写回任务、变量与完成记录。变量溢出不会部分提交任务。意外的游戏接口异常会中止演出；游戏结果动作没有跨接口整体回滚，不能宣称完整事务。

状态存于本作品命名空间的 `StoryKeyList/StorySave` 记录，随原版存档读写；不修改 `GameSave` schema 或官方任务资产。未保存的内存变化不等于磁盘存档。F5 单章试玩只预览演出，不携带事件任务配置或发放配置中的奖励；本轮没有启动 F5 或游戏。

## 编辑器弹窗

恢复、创建、重命名、导入、帮助和工具结果采用统一的应用内弹窗样式，提供右上角关闭、靠右的底部操作与 Esc 退出。关闭恢复提示只隐藏本次提示，不删除恢复副本；关闭未保存修改提示相当于取消切换，保留当前编辑。这些弹窗由 egui 绘制，系统窗口外框与应用内弹窗分开，不能称为系统原生弹窗。
